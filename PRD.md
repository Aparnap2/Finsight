# FinSight — Product Requirements Document

## Evidence-backed FP&A Intelligence System

**Version:** 1.0
**Status:** Draft
**Date:** 2026-07-28

---

## 1. Product Vision

FinSight is an **evidence-backed FP&A Intelligence System** that ingests financial data, validates its quality, computes KPIs and variances deterministically, generates evidence-grounded assertions, renders AI commentary under strict guardrails, and routes findings through governed approval workflows. Every monetary value is `decimal.Decimal`. Every claim is linked to source evidence. Every autonomy decision is policy-bound.

FinSight does not assist with FP&A — it performs FP&A under policy and human governance, but never writes to systems of record, never hallucinates financial figures, and never bypasses human approval for material decisions.

---

## 2. Problem Statement

FP&A teams spend 60–70% of each close cycle on mechanical work: importing actuals from multiple sources, reconciling spreadsheets, scanning for variances manually, emailing business partners for explanations, writing repetitive commentary narratives, and formatting board packs. This leaves insufficient time for strategic analysis, scenario modelling, and decision support.

Existing tools fall into two camps:
- **Spreadsheet-based workflows** — manual, error-prone, no audit trail, no automation
- **AI copilots** — generate text when asked, but do not own the workflow, enforce data quality, validate claims against evidence, or guard against hallucinated numbers

FinSight bridges this gap by providing a governed, evidence-driven intelligence layer that produces auditable, deterministic financial analysis augmented by LLM commentary under strict guardrails.

## 3. Non-Goals

The following are explicitly out of scope:

| Non-Goal | Rationale |
|----------|-----------|
| **Not a chatbot** | FinSight is not a conversational interface for ad-hoc finance questions. No open-ended Q&A. |
| **Not an ERP** | No transaction processing, no GL posting, no payables/receivables, no procurement. |
| **Not a BI tool** | No ad-hoc dashboards, no drag-and-drop analytics, no self-service reporting. |
| **No autonomous writes to systems of record** | Never posts to GL/ERP, never changes budgets, never approves payments, never deletes records. |
| **No real-time trading or market data** | Not a trading system. No real-time market feeds. |
| **No general-purpose LLM chat** | LLM usage is restricted to commentary rendering with validated inputs only. |
| **No custom ML model training** | Uses pre-trained LLMs via LiteLLM; no fine-tuned finance models. |
| **No full ELT pipeline** | No Spark, Airflow, or complex data engineering. Connectors are purpose-built for FP&A sources. |
| **No mobile app** | Web-first. |
| **No real-time collaboration** | Sequential review workflow, not simultaneous editing. |

## 4. Core Principles

| Principle | Description |
|-----------|-------------|
| **Deterministic calculations** | All financial computations — variance, materiality, KPI formulas, bridge decomposition — are pure deterministic Python using `decimal.Decimal`. No LLM involvement in any number. |
| **Evidence-backed AI** | Every assertion generated by the system must cite specific evidence records. The claim validator cross-checks every monetary figure in commentary against its evidence. Unsupported claims are rejected before publication. |
| **Human-in-the-loop** | The policy engine gates actions by confidence, materiality, and assertion type. Material variances, low-confidence findings, and action execution require human review. |
| **Typed interfaces** | All monetary values use `MoneyDecimal` (a `Decimal`-backed Pydantic type that rejects `float`). Assertions are typed by kind (numeric, comparative, causal, hypothesis, action). The API layer enforces type safety at the boundary. |
| **Context engineering** | LLMs receive only pre-validated, structured inputs — never raw data. The commentary renderer receives typed assertions; the root-cause agent receives bounded variance context. Context is constructed deterministically before any LLM call. |

## 6. User Journey

```
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │  Import   │───▶│ Validate │───▶│Compute   │───▶│ Detect   │───▶│ Generate │
  │  Data     │    │ Quality  │    │ KPIs     │    │Variances │    │ Evidence  │
  └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
       │                                                            │
       ▼                                                            ▼
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │  Context  │───▶│    AI    │───▶│ Validate │───▶│ Executive│───▶│  Export  │
  │  Builder  │    │Commentary│    │  Claims   │    │  Report  │    │  / Packs  │
  └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

**Step-by-step:**

1. **Import** — Data is ingested from PostgreSQL, CSV upload, or mock ERP endpoints
2. **Validate** — Data quality engine runs 6 deterministic checks (coverage, freshness, diversity, schema, filters, quality score). Failed checks produce degraded modes and block pipeline progression
3. **Compute KPIs** — The formula engine evaluates registered financial formulas via topological dependency resolution. All calculations use `decimal.Decimal`
4. **Detect Variances** — Variance engine computes actual-vs-budget for all accounts. Materiality engine applies tiered sensitivity thresholds (CRITICAL/HIGH/MEDIUM/LOW) to flag material deviations
5. **Generate Evidence** — The assertion pipeline transforms tool results and variance data into typed assertions, each with evidence IDs, support levels, and deterministic confidence scores
6. **Context Builder** — Assertions are structured into a `CommentaryRenderInput` that packages only validated truth for the LLM
7. **AI Commentary** — The LLM renders narrative text from the pre-validated assertions. It may arrange, paraphrase, and group claims but may not invent figures, causes, or actions
8. **Validate Claims** — The claim validator extracts every monetary figure from the rendered commentary and cross-verifies it against the evidence graph. Unsupported claims block publication
9. **Executive Report** — Verified commentary is structured into sections (executive summary, variance analysis, risks, actions)
10. **Export** — Results are available via API as structured JSON with both truth (assertions) and rendered (commentary) layers

## 9. Autonomy Policy Matrix

| Action | Auto-Run | Human Review | Hard Block |
|--------|----------|--------------|------------|
| Detect variance | ✅ | — | — |
| Assess materiality | ✅ | — | — |
| Run data quality checks | ✅ | — | — |
| Investigate root cause | ✅ | If confidence < 0.7 | — |
| Draft commentary | ✅ (before publish) | Always before publish | — |
| Propose actions | ✅ | Before execution | — |
| Publish management pack | — | Always | — |
| Update forecast assumptions (low impact) | ✅ | — | — |
| Update forecast assumptions (material) | — | Always | — |
| Create action items | ✅ (gated) | — | — |
| Send notifications | ✅ | — | — |
| Post to GL / ERP | — | — | ✅ Always |
| Change budget | — | — | ✅ Always |
| Approve spend / payments | — | — | ✅ Always |

## 11. Data Model

### Core Entities

| Entity | Definition | Key Attributes |
|--------|-----------|----------------|
| **Tenant** | Isolated organisation boundary | id, name, fiscal_calendar, base_currency |
| **FiscalPeriod** | Fiscal time bucket | id, tenant_id, fiscal_year, fiscal_period, start_date, end_date, status, prior_period_id, prior_year_period_id |
| **Variance** | Deviation from plan | account_id, account_name, department, actual_amount (Decimal), budget_amount (Decimal), variance_amount (Decimal), variance_pct (Decimal), is_material |
| **EvidenceItem** | Verified source record | source_table, record_id, field, value (Decimal), period, description |
| **RootCauseFinding** | Investigation result | variance_id, summary, assertions, evidence, confidence_score, alternative_hypotheses, data_gaps |
| **Assertion** | Typed evidence-backed claim | id, type (numeric/comparative/causal/hypothesis/action), text, value (Decimal), evidence_ids, support_level, confidence, source |
| **CommentarySection** | Rendered narrative | section_type, content, cited_data_points |
| **CommentaryDraft** | Complete commentary | sections, actions, assertions_used, version, status, approval_state |
| **ActionItem** | Follow-up task | id, action, domain, target, description, owner, status (proposed/approved/in_progress/completed/blocked/rejected), impact, policy_permitted |
| **ToolResult** | Standard evidence contract | data, row_count, coverage_pct, quality_score, freshness_seconds, schema_version, source_diversity, source_type, degraded_mode, query_fingerprint |

### State Machine: Period Run

```
initialized → data_validation → variance_analysis → investigation → commentary → review → completed
                  ↓                   ↓                    ↓             ↓         ↓
              blocked           [no material]        insufficient      rejected   revision
                              → commentary (skip)    → blocked
```

### State Machine: Investigation

```
created → evidence_gathering → analysis → findings_ready → completed
            ↓
         blocked → escalated
```

### State Machine: Commentary

```
drafted → claim_validated → under_review → approved → published
            ↓                  ↓
         blocked            rejected → revision
```

## 12. Feature Specifications — Key API Endpoints

### Pipeline Execution

```
POST /api/v1/pipeline/execute
  Body: { "period": "2026-06", "tenant_id": "CF001", "force": false }
  Response: { period, tenant_id, status, commentary[], assertions[], 
              degraded_modes[], data_quality, routing_decision, action_items[] }
```

### Commentary (Truth/Render)

```
GET /api/v1/commentary/{period}?tenant_id=CF001
  Response: { period, tenant_id, commentary[], assertions[], degraded_modes[], data_quality }
```

### Variances

```
GET /api/v1/variances/{period}?tenant_id=CF001
  Response: [{ account_id, account_name, department, actual_amount, budget_amount,
               variance_amount, variance_pct, is_material }]
```

### Bridge Analysis

```
GET /api/v1/bridge/{period}/{account_id}?tenant_id=CF001
  Response: { account_id, account_name, total_variance, bridge_type,
              components[], reconciles, confidence, degraded_modes[] }
```

### Data Quality

```
GET /api/v1/data-quality/{period}?tenant_id=CF001
  Response: { overall_score, passed, degraded_modes[], checks[] }
```

### Policy Decision

```
GET /api/v1/policy/{period}?tenant_id=CF001
  Response: { autonomy_level, routing_target, reasons[], requires_review,
              blocked_actions[], confidence }
```

### Actions (Gated)

```
POST /api/v1/actions
  Body: { action: "reduce", domain: "cost", target: "...", description: "...",
          cited_assertion_ids: [], owner: "...", impact_expected_savings: "50000",
          policy_permitted: true }
  Response: { id, action, domain, description, status, policy_permitted, ... }
  Errors: 422 if any gate fails — returns structured errors + warnings
```

## 14. Out of Scope

The following are explicitly out of scope for this version and are not planned for any future iteration:

- **Enterprise Resource Planning** — No transaction processing, order management, inventory, procurement, or supply chain
- **Payroll systems** — No salary computation, tax withholding, benefits administration
- **General Ledger** — No journal entries, no GL posting, no trial balance management
- **Workflow / BPM** — No general-purpose workflow engine, no BPMN, no custom workflow builder
- **Authentication / Authorisation** — No SSO, RBAC, or user management (assumes gateway-level auth)
- **Billing / Invoicing** — No customer billing, no invoice generation, no payment processing

- **General-purpose chatbot** — No open-ended Q&A, no conversational AI

## 15. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| LLM hallucinates financial numbers | Medium | Critical | Claim validator, truth/render separation, evidence graph, HITL approval |
| Free-tier API rate limits | High | Medium | LiteLLM fallback, caching, rate limiting |
| Source data quality issues | High | Medium | Data quality gate, degraded mode propagation, remediation workflow |
| Human approval bottleneck | Medium | High | Policy-based auto-approval for low-risk items |
| Tenant data isolation failure | Low | Critical | Row-level security, strict query scoping, tenant_id on every query |
| Workflow state corruption | Low | Critical | LangGraph checkpointing, idempotent operations |
| Prompt injection | Medium | High | Input validation, bounded tool access, structured outputs |
| Model drift / performance regression | Medium | Medium | Continuous eval, claim validator catch rate monitoring |
